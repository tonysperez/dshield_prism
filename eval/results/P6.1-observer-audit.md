# P6.1 — `observer.name` propagation audit (multi-sensor readiness)

**Date:** 2026-06-04. **Context:** the read-side follow-up to D3 (session-ID
namespacing). The deployment is **1 sensor** today, and Cowrie emits no sensor
name, so `observer.name` is `default`/absent everywhere — every issue below is
**latent** until the 2nd/3rd sensor lands. This audit records where sensor
identity lives, where it drops (and whether that's correct), and the spec for
the deferred multi-sensor fixes.

## Propagation trace

| Layer | Carries `observer.name`? | Verdict |
|---|---|---|
| Raw event (`prism.raw.cowrie.session`) | Set at ingest by the per-sensor wrapper pipeline (`setup/create-sensor-pipelines.sh`) | ✅ source of truth |
| **Session rollup** (`prism.rollup.cowrie.session`) | **Yes — now always** (P6.1 fix below). Drives the namespaced `_id` `<sensor>:<session_id>` | ✅ fixed |
| Command enrichment (`prism.enriched.cowrie.command`) | `observer.type`/`vendor` only (static "honeypot/Cowrie"), **no name** | ✅ correct — commands are content-deduped across sensors (one doc per sha16); a sensor name would be ambiguous |
| Cluster centroids / playbooks / campaigns / operations / anchors | No | ✅ correct by design (D4: behavioural identity is cross-sensor) |
| **IP rollup** (`prism.rollup.cowrie.ip`) | No | ⚠️ gap — an IP is multi-sensor; the rollup can't say *which* sensors saw it |
| **`source_ip` lifecycle** | No | ⚠️ gap (same — multi-sensor IP) |
| **Findings** (`prism.finding`) | No | ⚠️ partial gap — session-scoped findings can't attribute a sensor (most findings key on cross-sensor playbooks/campaigns/IPs, so lower impact) |
| **Console** | Never read, displayed, or filtered | ⚠️ gap — no per-sensor view; `lookup_session` doesn't disambiguate (below) |

## Cross-sensor read collision (the core latent bug)

The rollup `_id` is collision-safe (`<sensor>:<session_id>`), but **~16 reads
key on the `cowrie.session_id` *field*** (not `_id`) across enrich
(`commands.py`, `sessions.py`, `explain.py`) and console (`queries.py`,
`graph.py`, `server.py`, `findings.py`). Under a cross-sensor session-ID
collision these return the wrong/arbitrary session. No reader uses the
collision-safe `_id`, because none has the sensor in context.

`console.queries.lookup_session(session_id)` is the clearest example:
`query={"term": {"cowrie.session_id": session_id}}`, size-1, no sensor filter.

## Fix applied now (correct + validatable with 1 sensor)

**Session rollup always stamps `observer.name`** (`_build_session_doc`,
`sessions.py`): events without one default to `_DEFAULT_SENSOR`, so the doc's
`observer.name` always equals its `_id` namespace prefix. Previously the `_id`
said `default:` while the field was absent — so a future `observer.name` read
filter would have missed every existing session. This makes the disambiguation
key reliably present. It changes `_build_session_doc`'s source, so the
`rollup_schema_hash` (P1.1) flips and the next backward pass re-pools once to
backfill the field (idempotent — `_id` is unchanged). Smoke:
`scripts/smoke/smoke_test_observer_name.py`.

## Deferred to the multi-sensor rollout (spec)

These need a 2nd sensor to build/validate against, so they ship **with** the
per-sensor pipeline deployment, not now:

1. **Session read disambiguation (highest priority).** Plumb a sensor selector
   through the console (URL/UI) and the session-by-id reads; resolve by the
   namespaced `_id` when the sensor is known, or add an `observer.name` filter
   to the `cowrie.session_id` field queries. Enabled by the fix above.
2. **Console sensor surface.** Fetch + display `observer.name` on session views;
   add a per-sensor filter to the inbox/graph.
3. **IP rollup / `source_ip` lifecycle `observed_by`.** Aggregate the set of
   sensors that saw an IP (new agg in the IP rollup builder) so cross-sensor IP
   attribution is answerable. Additive field.
4. **Session-scoped findings** may carry the originating sensor; revisit per
   finding kind (most are cross-sensor and need no change).

## Not a gap (recorded so it isn't "fixed" by mistake)

Commands, clusters, playbooks, campaigns, and operations are **cross-sensor by
design** (content-addressed / behavioural identity, D4). Do **not** add
`observer.name` to them — it would imply a per-sensor scoping the model
deliberately rejects.
